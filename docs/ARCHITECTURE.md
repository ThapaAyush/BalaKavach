# KidsGuard architecture

## Current implementation (Stages 1–7)

KidsGuard is a JavaScript monorepo managed with npm workspaces:

- `apps/web` is a React and Vite browser app. Tailwind CSS is integrated through the Vite plugin. The parent page supports registration, login, session restoration, logout, and child-profile CRUD. For Stage 6, it integrates ephemeral in-memory pairing code generation, countdown display, unredeemed code cancellation, family-scoped paired device listing (showing child association, platform, paired timestamp, last seen, and status), and device revocation. The frontend holds pairing codes strictly in React component state; codes are never written to `localStorage`, `sessionStorage`, cookies, or logs. Lifecycle guards and `AbortController` prevent late-arriving responses from displaying stale codes after sign-out, child context switching, or component unmount.
- `apps/api` is an Express REST API. It implements health, parent authentication, parent-scoped child-profile CRUD, pairing-code issue/revocation/redemption, parent-scoped device listing/revocation, device bearer authentication, and the device heartbeat endpoint beneath `/api/v1`.
- `apps/extension` is a Chrome Manifest V3 extension. In Stage 5, it established local domain navigation filtering using `declarativeNetRequest`. In Stage 7, it integrates device pairing and presence tracking with the backend API:
  - `src/device-client.js`: Normalizes API base URLs (requiring HTTPS for non-local hosts and allowing local HTTP), validates 22-character base64url codes and 43-character device credentials strictly, communicates with `POST /device-pairing/redeem` and `POST /devices/heartbeat`, handles offline network errors gracefully, and interprets HTTP 401 neutrally as `invalid_session` without claiming parent revocation.
  - `src/service-worker.js`: Manages the extension background lifecycle, recovers and reconciles a 15-minute `kidsguard_heartbeat` alarm via `chrome.alarms` on startup without resetting active timers, validates message sender identity (`sender.id === runtime.id`, rejecting web tabs and external origins), strictly validates input fields, sanitizes outgoing device payloads, and halts heartbeat requests during `invalid_session` states while retrying on temporary network or server errors.
  - `popup.html`, `popup.css`, `popup.js`: Provides a pairing form with client-side validation and duplicate submission guards, displays sanitized device status badges (`Unpaired`, `Paired`, `Re-auth required`), shows heartbeat timestamps with offline notices, provides an explicit unpair/reset action with confirmation, and clearly discloses that remote policy synchronization is not implemented yet.
  - Domain blocklist rules remain completely decoupled from device pairing and heartbeat states; pairing failures, 401 responses, and unpairing actions never alter or flush active `declarativeNetRequest` rules.
- MongoDB access is configured through Mongoose and the backend-only `MONGODB_URI` environment variable. Parent records store normalized email and Argon2id password hashes; parent sessions store hashes of cryptographically random tokens with explicit expiration. A unique Family belongs to one parent, ChildProfile records are scoped to that family, and device registrations retain the same family and child scope.
- Pairing codes contain 128 bits of random material; only SHA-256 hashes are stored. A conditional atomic update claims a code once when it is unexpired and not revoked. Device credentials contain 256 random bits (43-character base64url); only their SHA-256 hashes are stored, and the raw credential is returned once in the successful enrollment response.
- Device authentication middleware (`requireDeviceAuth`) extracts bearer credentials from `Authorization: Bearer <deviceCredential>`, enforces length limits (<= 256 bytes), validates base64url format, hashes with SHA-256, and verifies the device is not revoked. The heartbeat endpoint (`POST /devices/heartbeat`) updates `lastSeenAt` conditionally using `{ _id: deviceId, revokedAt: null }`, preventing concurrent revocation bypasses. In-process rate limiting protects the endpoint, with support for shared production stores.
- API tests inject isolated in-memory repositories and do not connect to MongoDB. In-memory repositories simulate atomic operations and timing-safe secret comparisons. Live MongoDB Atlas multi-process parallel writes, reconnection races, index performance, and shared rate-limiting stores (e.g. Redis) remain unverified. `enforcementStatus` is strictly `not_implemented` across all models and UI displays.

The API has separate config, controller, middleware, model, route, service, validator, and utility directories. Device registration and heartbeat provide enrollment and presence tracking only: there is no activity collection, website/app blocking, or Android monitoring in this stage.

## Chrome extension architecture (Stages 5 & 7)

The extension is a separate Chrome Manifest V3 workspace.
- **Local Domain Filtering**: Stores a normalized local blocklist in `chrome.storage.local` and applies top-level navigation block rules through `declarativeNetRequest.updateDynamicRules()`. Rules match each configured domain and its subdomains for `main_frame` requests. The list is capped at 100 entries and the extension modifies only its reserved dynamic-rule ID range.
- **Device Pairing & Presence**: Authenticates to the backend API via a 256-bit bearer device credential obtained by redeeming a single-use 128-bit pairing code. The raw device credential is held exclusively within the service worker and `chrome.storage.local` session storage; the popup UI only receives sanitized status objects.
- **Heartbeat Scheduling**: Schedules a 15-minute background heartbeat using `chrome.alarms` (`kidsguard_heartbeat`). Reconciled idempotently on service worker boot, `onInstalled`, and `onStartup`. Heartbeats stop during `invalid_session` states until explicit re-pairing or reset.
- **Permissions**: Declares `alarms`, `declarativeNetRequest`, and `storage`. Host permissions are strictly restricted to local development endpoints (`http://localhost:5000/*` and `http://127.0.0.1:5000/*`). Production deployments must update the manifest to specify the dedicated production HTTPS API origin.
- **Isolation**: Domain blocklist rules operate entirely in the local browser profile and are independent of backend availability. Heartbeat offline errors, API outages, and device unpairing actions do not alter or remove configured blocklist rules.

## Request path

The browser uses `apps/web/src/lib/api.js` to send credentialed requests to `VITE_API_BASE_URL`. The API applies security headers, a single credentialed CORS origin, request IDs, safe request logging, JSON size limits, and API/authentication/pairing/heartbeat rate limits. Parent mutations require the configured `Origin`. Child lookups and device operations derive the family from the authenticated parent and include that family ID in repository filters; cross-family misses do not disclose whether a record exists. Enrolled devices authenticate requests using bearer tokens in the `Authorization` header.

The extension service worker uses `apps/extension/src/device-client.js` to send requests to the configured API base URL (defaulting to `http://localhost:5000/api/v1`). It redeems codes via `POST /device-pairing/redeem` and sends periodic heartbeats via `POST /devices/heartbeat`.

## Next stages

Multiple caregivers, remote policy synchronization, server-managed website enforcement distribution, browser tamper resistance, Android accessibility/VPN monitoring, enforcement synchronization, and deployment hardening remain unimplemented. The extension provides local Chrome navigation filtering and presence heartbeat only. Architecture decisions for future stages must preserve server-side authorization, least data collection, and honest enforcement reporting.
