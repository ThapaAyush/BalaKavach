# Database status

The API uses Mongoose and reads the MongoDB connection string from `apps/api/.env` as `MONGODB_URI`. The example file contains placeholders only. Keep the real connection string on the backend and never put it in a `VITE_` variable.

The API stores parent accounts in the `parents` collection. Emails are trimmed, lowercased, and protected by a unique index. Passwords are stored only as Argon2id hashes. Parent sessions are stored in the `parentsessions` collection; only SHA-256 hashes of random session tokens are stored. Sessions have an expiry timestamp and a TTL index, while every request also checks expiry directly. Startup creates the required indexes before enabling authentication; if the database or indexes are unavailable, authentication fails closed with a service-unavailable response.

The API can still start without a connection string so the health endpoint and frontend shell can run locally. In that case health reports MongoDB as disconnected and authentication is unavailable. When a URI is configured, startup attempts a TLS-capable MongoDB connection. If it cannot connect, the API logs a generic warning and starts in degraded mode. Live Atlas persistence has not been verified as part of this Stage 2 work; automated auth tests use an in-memory repository.

Each parent has at most one `families` document, with a unique immutable `ownerParentId` reference to `parents._id`. The family document is created on the first child-profile creation. `childprofiles` documents reference that family through an immutable `familyId` and store a required `displayName` plus an optional date-only `dateOfBirth`. A unique owner index enforces one family per parent; a `{ familyId, createdAt, _id }` index supports scoped listing. No TTL cleanup is used for family or child authorization.

Child-profile queries always use the family found from the authenticated parent session. The API does not accept a family ID or parent ID as an ownership input. Child profiles and family documents are not returned with their ownership fields. Startup creates the required family/child indexes before enabling these operations; database outages or missing indexes fail closed with a generic `503`.

The family and child test suite uses an isolated in-memory repository and also checks fail-closed behavior without MongoDB. The auth, family, and child indexes were successfully ensured in the supplied Atlas database during setup, but registration/session writes and family/child CRUD persistence or isolation were not exercised. Existing Atlas data was not reset.

Stage 4 adds `pairingcodes` and `deviceregistrations` collections. PairingCode stores a unique SHA-256 `codeHash`, immutable `familyId`, `childProfileId`, and `createdByParentId`, `expiresAt`, `redeemedAt`, and `revokedAt`. It has a unique hash index, a family/child/created-time index, and an `expiresAt` TTL index for cleanup. Redemption also filters on `expiresAt > now` and null `redeemedAt`/`revokedAt`; authorization never relies on TTL cleanup.

DeviceRegistration stores immutable `familyId`, `childProfileId`, and unique `pairingCodeId`, a unique SHA-256 `credentialHash` (excluded from normal reads), device name/platform, `pairedAt`, nullable `lastSeenAt`, and nullable `revokedAt`. Family/time and family/child/time indexes support parent-owned listing. Device IDs are generated by MongoDB/Mongoose; clients cannot select ownership fields.

Redemption uses an atomic conditional `findOneAndUpdate` on one pairing record to set `redeemedAt`. Only the request receiving the updated record proceeds to check the child and insert a DeviceRegistration. The unique `pairingCodeId` index is an additional database constraint against registering a second device from one code. This avoids requiring a multi-document transaction for single-use protection, subject to verifying MongoDB behavior in integration testing.

The code claim and device insert are separate writes. If insert failure is known, the code remains consumed and a replacement code is required; it is never reopened because doing so after an uncertain write could permit duplicate enrollment. If a timeout or connection loss occurs after MongoDB committed the insert but before the response arrived, a registration can exist while the client has not received its one-time credential. The parent can find and revoke that registration, then issue a new code. A multi-document transaction could make claim and insert commit together, but cannot guarantee delivery of the one-time credential after a committed transaction; this stage uses the simpler single-document claim and documents the recovery path. Stage 4 MongoDB index creation, TTL behavior, real concurrent redemption, and failure recovery have not been integration-tested. No Atlas connection was made for Stage 4.
